# Satis Factorio Program (C++)

The factory game, rewritten from Python/pygame in C++17 with [raylib](https://www.raylib.com).
Gameplay, controls, art and save files are the same as in the Python version.

## Build & run (Windows)

1. Run `install_cpp.bat` once. It installs MSYS2, g++, raylib and CMake.
2. Run `build.bat`. It creates `factory_game.exe`.
3. Start `factory_game.exe`.

Other options:

* `build.bat debug` builds with a console window and debug info.
* `build.bat test` builds and runs the simulation tests.

If you prefer CMake: `cmake -B build -G "MinGW Makefiles"`, then `cmake --build build`.

## Play in the browser (Chromebook)

The game also runs in the browser: https://markuscampidell.github.io/factory-game/
Saves there are kept in the browser (separate from the Windows saves). There's no Quit button - just close the tab.

* One-time setup on this PC: create an empty public repository called `factory-game` on GitHub, install Git (https://git-scm.com/download/win), run `setup_github.bat`, then on GitHub: Settings -> Pages -> Source: GitHub Actions.
* Updating: run `publish_web.bat`. GitHub runs the simulation tests, builds the browser version (`web/build_web.sh`, Emscripten + raylib) and puts it online in about 3 minutes. Reload the page on the Chromebook.
* The workflow is `.github/workflows/web.yml`; if the tests fail, nothing is published.

## Project layout

| Folder | What's in it |
|---|---|
| `src/core` | Items, recipes, inventories, item filters |
| `src/sim` | The simulation: world, chunks and tiles, terrain, belts and transport, machines, building and deleting, saves. It doesn't depend on raylib. |
| `src/game` | Window, input, drawing, menus and all UI panels |
| `tests` | Headless tests for the simulation |
| `assets` | Sprites, copied from the Python version |
| `saves` | Save files. The format is the same JSON as the Python version, so saves load in both. |

## What changed compared to the Python version

### Belts are 100% efficient

* The simulation runs at a fixed 60 ticks per second, and every timer is an integer number of ticks. No floating point means no rounding and no dependence on frame rate.
* A belt tile takes exactly 15 ticks to cross, so a belt moves 4 items/s.
* Each tick, belts are processed from the downstream end backwards. When an item leaves a tile, the tile behind it refills in the same tick. No time is lost between tiles, so a full belt delivers exactly 240 items per minute at 1 tile or at 5000 tiles.
* Merges alternate fairly with no gaps. Splitters split evenly with no gaps. A completely full belt loop keeps moving.
* The tests check all of this by counting the items that arrive at the end of the belt.

### Items are never created or destroyed

* Building, deleting and replacing are tried on a copy of your inventory first. They only happen if everything fits. Refunds include everything inside the building.
* Switching a machine's recipe is blocked if its items wouldn't fit in your inventory. Python lost them.
* A machine won't finish a batch whose inputs were taken out while it was running. Python created the outputs anyway.
* Inventory removal is all-or-nothing. Python could remove items partially.
* The `I` debug key that created items is removed, and so are the test recipes.
* When loading a save, any item that can't be put back is given to you instead of disappearing (for example, items in a machine whose recipe no longer exists).
* The tests run 6000 random build, delete, recipe-switch and simulation steps and check that the item totals never change.

### Other

* The tile system and chunks (32x32 tiles) work as before. Terrain is generated by the same algorithm, so the same seed gives exactly the same ore patches as in Python. A test checks 65,536 tiles against the Python output.
* Performance: 100,000 belts take about 1.7 ms per simulation tick.
* Items without a sprite (limestone, concrete) are drawn as labeled tiles, so limestone patches are visible now.
* Iron Plate recipe: 3 Iron Ingot gives 2 Iron Plate in 6 s. The old one was a test recipe that gave 40 plates and 40 coal.
* A new game starts with 500 iron and 200 copper ingots (Python: 4300 iron, which filled the whole inventory).
* Zoom: mouse wheel (around the cursor) or `+` / `-`, from 10% to 300%. Below 40% the game switches to a map view: machines are colored boxes, belts are gray, ore is shown as colored pixels. In map view WASD pans the map, the player can't move, and building or deleting is disabled (build mode is reset to None).
* Hand mining: hold right click on an ore tile (1 ore every 4 s, half a Miner's speed). If the inventory is full, "Inventory full" appears next to the tile and the ore stays in the ground.
* Copy / paste: Shift + right click copies a machine's recipe, a belt's filter or a splitter's three filters (three separate clipboards). Shift + left click pastes; keep it held and sweep the mouse to paste onto many objects. A message above the object says what happened, or why it didn't work.
* Bottom right, next to the hotbar: a Blueprints button (opens the blueprint list, like B) and an Alt button that shows / hides the output icons on machines (lit up = shown). Pressing Alt on its own does the same. Hovering over these buttons, the Menu button or a hotbar slot shows its name. Menu and Blueprints light up while what they open is open.
* Everything clickable gets slightly brighter under the mouse; inventory / storage / machine slots get a light highlight. Recipes (machines and hand crafting) are buttons; the selected one is lit up with a white outline. Hotbar names also show the build cost.
* Panels: at most two at once - the Inventory alone or together with a machine, storage or Handcrafting panel. Blueprints, belt filter and splitter filter are always alone. Open panels sit side by side (Inventory left) and are centred as a group. Opening a panel closes the others; closing one of a pair closes both. The Game Menu closes all panels; Save As, Controls and the exit question open on top of it and return to it.
* ESC closes the item picker, then the open panel(s), then leaves build mode, then opens the Game Menu. Inside the Game Menu, ESC goes back one step (Save As / Controls / exit question -> Game Menu -> game). The blueprint list stays open in map view. The Alt setting is saved with the game.
* UI size: every UI is laid out for a window of at least 1100 x 700. In a smaller window (e.g. a browser with tabs and address bar) all UI - panels, menus, dialogs, hotbar, HUD - is drawn smaller by the same factor, so nothing is too big for the screen and the proportions stay the same. The world is not scaled. Text is rendered at its real size, so it stays sharp. Panels are centred in the space above the hotbar. (`ui::updateScale` in `src/game/Ui.cpp`.)
* All panels, dialogs and menus share one look (purple panel, centred bold title, red X in the top-right corner to close it). The colours and sizes live in one place, `ui::` in `src/game/Ui.hpp`.
* Middle click on a machine, belt or splitter picks it up: you build more of the same type, facing the same way. Recipe and filters are not copied (new ones start at their defaults). It isn't saved anywhere and Ctrl + V ignores it.
* Item messages: building, deleting (one object or Ctrl + X), and placing a copy or blueprint show what changed in your inventory above the object, e.g. "-10 Iron Ingot, -5 Copper Ingot" or "+1 Copper Ingot, +2 Iron Ingot". While holding a machine, belt line or blueprint, a box at the top shows "Needs: ..." (red if you don't have enough).
* Copy & paste many things: Ctrl + C, drag a rectangle over machines/belts (recipes, filters and directions are kept), then click to place it. Ctrl + V places the last copy again. Placing needs free space, ore under miners and the full build cost in your inventory; otherwise nothing happens.
* Placing over existing things (machines, belt lines, copies and blueprints - all the same rules): identical things underneath (same type and position; belts and splitters also the same direction) don't block and cost nothing; their settings are updated. Shift replaces everything else: a belt or a machine of the same type at the same spot is turned/updated in place and keeps its items (a machine only hands its items to you if its recipe actually changes); anything different is removed and refunded. "Needs: ..." counts only what is actually new.
* You can only build in chunks you have already discovered (seen in the normal view). A blueprint that reaches into an undiscovered chunk shows those parts darkened and can't be placed.
* Map view: press M or the Map button (bottom right, next to Alt) to switch to the map around the player and back to the zoom you had. Zooming out with the mouse wheel still works too.
* Alt mode also shows the output icons in copy/blueprint ghosts and the default recipe of a machine you're about to place.
* Selections (Ctrl + C, Ctrl + B, Ctrl + X) are at most 128 x 128 tiles (4 x 4 chunks); dragging further just stops at that size. Machines that stick out of the rectangle are taken whole, but only if the result still fits in 128 x 128 - a machine touching the edge of a full-size selection with one or two tiles is left out. The highlight shows exactly what will be taken.
* Blueprints: Ctrl + B, drag a rectangle, then a dialog lets you name it and Save blueprint (or Reselect; ESC / click outside cancels). B opens the blueprint list (Add / Use / Delete). Blueprints are shared by all saves (saves/blueprints.bpjson). Right click returns to normal building, ESC cancels.
* Delete many things: Ctrl + X, drag a rectangle - everything inside (and machines sticking into it) is removed with its contents and refunded, but only if it all fits in your inventory. Right click returns to normal deleting, X alone leaves delete mode.
